## 3. The incident: how a docs/reconciliation session almost took mail down, and the actual fix

This is worth reading in full if you're going to do any more git surgery on the VPS checkout.

**Discovery.** While preparing to rebuild production with latest code, `git status` on `/home/ubuntu/AVRY-Mail` (the VPS checkout) showed 31 files of uncommitted local changes — including migration files that had apparently been renumbered, and evidence (timestamped backup folders `.deploy-backups/phase3-rollout-20260912T024653Z/` and `.deploy-backups/phase5-canary-20260912T043633Z/`, both from *before* this session started) that someone had done substantial unrelated MCP-related work directly on the server, never committed.

**Reconciliation.** Rather than guess which side was authoritative:
1. Committed the VPS's entire uncommitted state to a new branch, `vps-server-snapshot-20260912`, excluding `.deploy-backups/` and `.security-backups/` (both contain raw `.env` copies with production secrets — never git-add those directories).
2. Discovered the VPS's tracked `main` branch was **14 commits behind** `origin/main` (a stale fetch cache made it look like only 1). The 14 missing commits included legitimate, already-reviewed hardening work. This meant the VPS's ad-hoc "Phase 3/5" uncommitted work was built on a stale base and largely duplicated things already properly merged upstream — it was safe to leave behind on the snapshot branch rather than reconcile file-by-file.
3. Fast-forwarded VPS `main` to `origin/main`, then to the newly-pushed Phase 2 commits.

**The mistake.** Step 1's sequence — `git checkout -b snapshot`, `git add -A && commit`, then `git checkout main` — has a consequence that's easy to miss: any file that was *untracked* before the snapshot commit, and got swept up by `git add -A` into the snapshot branch, becomes **tracked only on that branch**. Switching back to `main` then makes git correctly remove it from the working directory, because `main`'s tree doesn't have it and git is doing exactly what checkout is supposed to do. This silently deleted:
- `docker-compose.mail-prod.yml` and its hardening overlay (never committed anywhere before tonight),
- migrations 026–028 (already applied to the production database, but likewise never committed).

Neither deletion was visible until the actual rebuild+redeploy: the build itself succeeded (Docker only needs the files present on disk at build time, and they still were, briefly, before other operations reset the tree state), but the fresh binary's `sqlx` migrator refused to start with `migration 26 was previously applied but is missing in the resolved migrations` — because by the time of `up -d`, those files were gone from the working directory the image was built from in a subsequent rebuild. **This put `avry-mail` into a genuine crash-restart loop in production.**

**The fix**, done live: restored the three migration files and the two compose files from the `vps-server-snapshot-20260912` branch (`git checkout vps-server-snapshot-20260912 -- <path>`), rebuilt, redeployed — healthy within a few minutes. Then, properly, committed all five files to `main` and pushed, so this exact failure mode can't recur on a future clone or branch operation.

**Takeaway for next time:** if you need to snapshot a dirty working tree before switching branches, prefer `git stash -u` over `commit-then-checkout`. A stash doesn't reassign which branch "owns" a file the way a commit-and-switch does, so it can't produce this deletion. If you do use commit-and-switch, immediately diff `git status` on the branch you land back on and treat any unexpectedly-vanished file as a five-alarm signal before doing anything else — including a build.
